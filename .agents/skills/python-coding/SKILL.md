# Python 编程规范

## 核心准则

1. **不要过度设计。** 优先复用 Python 标准库、项目已有能力和成熟开源包的现成功能。第三方包必须有广泛实际使用、稳定 API、可靠文档和持续维护，不能为省几行代码引入小众包。新增依赖前确认项目兼容性与维护状况；现有能力够用时不另造轮子。没有合适的成熟能力时，用尽量少且清晰的代码实现当前需求，不为假想的未来需求搭建框架、层级或扩展点。
2. **保持最大人类可读性。** 代码应让人容易理解。使用明确命名、直接控制流和适度长度的函数；不要用压缩表达式、晦涩技巧或多层转发换取表面上的行数减少。按功能拆分模块，每个模块职责清晰，遵循项目已有边界和命名约定。
3. **集中公共逻辑。** 避免同类代码片段散落在多个位置。被多处复用的逻辑提取到职责明确、按用途命名的公共 Python 文件中，由调用方统一导入；优先复用已有公共模块。不要建立无所不包的工具文件，也不要把仅使用一次的简单逻辑提前抽象成公共框架。

## 哈希计算的必要性

- **非必要不引入哈希值计算。** 新增前明确哪个实际行为依赖该值，以及为什么现有业务 ID、版本号或直接比较不能满足需求；不能以“以后可能用到”为理由添加哈希。
- **仅用于记录时，不计算哈希。** 不为日志、元数据、实验报告或追踪字段单独计算内容、配置、文件或目录的哈希；优先记录已有标识、版本和必要的可读信息。
- 只有实际参与完整性校验、内容寻址、去重、缓存失效判断或安全协议等功能，且确有必要时，才使用哈希；必须有实际消费该值的比较、校验或协议逻辑，不能只生成并保存。优先复用已有可信摘要，避免重复读取和计算。
- 此规则不限制 `dict`、`set` 等 Python 容器内部的正常哈希行为。审查现有显式哈希计算时，先确认用途和数据契约，再按当前任务范围清理无实际用途的计算，不直接删除仍影响功能正确性的校验。

## 语言规范

- **代码及其注释始终使用英文，禁止使用中文。** 包括模块、类、函数、参数和变量命名，行内与块注释，所有文档字符串，以及代码中编写的日志、异常和提示信息。
- Google 风格文档字符串中的功能、参数、返回值、异常及数据字段含义说明全部使用英文；文档中的代码示例也遵循同一规则。
- **只有独立文档优先使用中文**，例如 README、设计说明、使用指南和本技能说明。源代码内的 docstring 属于代码注释，不属于中文文档例外。此处只规定已有或确有需要的独立文档所用语言，不要求创建 README 或其他文档。

## 项目目录结构

按实际需要创建目录，不预建空目录。目录职责统一如下：

| 目录 | 用途 |
| --- | --- |
| `config/` | YAML、JSON、TOML 等配置文件；与源码内定义配置类的 `config.py` 区分。 |
| `scripts/` | 可复用的功能脚本、操作入口与数据集下载脚本。 |
| `scripts/analyze/` | 实验结果分析脚本；除非有特殊要求，默认不纳入 Git 管理、不上传远程仓库。 |
| `data/` | 数据集。 |
| `output/` | 实验输出数据。 |
| `src/<package_name>/` | 具体 Python 包的代码。 |
| `.local_doc/` | 不需要上传远程仓库的本地临时开发文档。 |
| `docs/` | 正式项目文档。 |
| `resources/` | 算法运行所需的非数据集资源。 |
| `dockers/` | Docker 相关构建与运行文件。 |
| `third_party/` | 第三方依赖的代码仓库。 |
| `assests/` | 正式文档依赖的图片等静态素材；使用此约定拼写。 |
| `.tmp/` | 临时脚本。 |

### 测试目录

- **只有模块在自身目录维护 `tests/`**，例如 `src/<package>/tests/`。
- `scripts/` 一般是脚本目录，不作为模块单独设置 `tests/`；脚本测试统一放在根目录的 `tests/scripts/`。
- 根目录 `tests/integration/` 仅放跨模块联调测试。
- 新增或移动测试时，按被测行为的归属放置，并同步维护测试发现配置、路径引用及运行文档。

### 文档边界与存放位置

- **不默认为每个模块或子模块创建 README。** 新增、拆分或重构 Python 模块不构成新增 README 的理由；不得按源码目录层级逐级配套生成说明文档。只有用户明确要求或项目现有规范明确要求时，才在模块目录新增独立文档。
- 项目概览与使用入口放在项目根 README；需要长期维护的架构、算法和使用说明集中放在 `docs/`，优先更新已有相关文档，不重复复制到各个子模块。
- 开发计划、任务进度、调试记录、重构过程和临时验收记录等过程信息，如需落盘，放在默认不纳入 Git 的 `.local_doc/`；不放入 `src/` 或其他算法源码目录，也不写入代码注释或 docstring。代码内只保留理解当前实现所需的功能、接口、设计意图和约束说明。
- 本规则约束本次新增或修改的内容；不据此批量删除项目已有文档。

### 配置与脚本的目录层级

- `config/` 按场景、功能、测试数据集等实际维度分类。只有目的完全相同、仅参数不同的配置文件可以放在同一末级目录；目的不同的配置必须分目录。
- `scripts/` 遵循相同的分类、同目的分组和深度规则，不把不同用途的脚本散放在同一目录。`scripts/analyze/` 是分析脚本的固定入口。
- **最多两层子目录**，从 `config/` 或 `scripts/` 之下开始计数，根目录和文件名不计入层数。例如 `config/train_search/searchqa/default.yaml` 和 `scripts/analyze/searchqa/compare.py` 均为两层子目录。
- 分类维度超过两层时，把额外维度合并为清楚的目录名并平铺，例如 `config/train_search_grpo/searchqa/default.yaml`；不要继续增加目录深度。相同目的的参数变体用文件名区分，例如 `seed_1.yaml`、`seed_2.yaml`。

### 本地文件与 Git 管理

- `.local_doc/`、`.tmp/`、`.env` 默认加入 Git 忽略规则；`scripts/analyze/` 除非用户有特殊要求，也必须忽略，不提交或上传远程仓库。
- `.env.example` 应纳入 Git 管理，不能被宽泛的 `.env*` 忽略规则误排除。
- 新增忽略规则时检查文件是否已被 Git 跟踪；忽略规则不会自动取消跟踪。需要取消跟踪时保留本地文件，不通过删除文件实现忽略，也不自动重写仓库历史。

### 数据集下载可复现

需要下载新数据集时，**必须在 `scripts/` 下创建可完整下载该数据集的脚本，并纳入版本管理**，不能只手工下载，也不能只把下载命令留在会话或临时目录中。下载脚本不放入默认忽略的 `scripts/analyze/`。

脚本应明确数据来源、版本或修订标识、所需数据划分及目标路径，完成必要的下载、解压和目录整理，使其他人能获取同一版本并得到项目配置所期望的 `data/` 路径。数据源提供可信校验和时，用于验证下载文件的完整性；不为仅记录而自行计算校验和。重复执行不应静默切换到新版本。数据源需要认证或许可时，说明前置条件并从环境读取凭据，不把个人凭据写入脚本。

### 环境文件同步

- 修改 `.env` 时，在同一次改动中同步 `.env.example`：新增或删除变量定义时，两边必须同步新增或删除；`.env.example` 不存在时创建。
- **非隐私配置的值也必须实时同步**，包括 Docker 端口、默认配置路径等；即使只改值、没有改变量名，也要更新 `.env.example`。
- API key、私有 base URL、密码等隐私配置只同步变量名和必要的英文说明，`.env.example` 中使用空值或明确的公开示例占位值，不复制真实隐私值。
- `.env` 不纳入 Git 管理；`.env.example` 纳入 Git 管理。同步时核对变量集合及非隐私值是否一致，不在日志或报告中输出隐私值。

### 环境变量名称常量

- **代码中读取 `.env` 或进程环境时，环境变量名称必须定义为字符串常量并统一引用，禁止在读取位置直接硬编码变量名字符串。** 此规则覆盖 `os.getenv()`、`os.environ`、dotenv 解析结果的键访问，以及配置框架的环境变量别名等映射。
- 常量集中放在职责对应的公共 `constants.py` 中；已有明确的公共常量模块时复用它。同一个环境变量名只维护一份定义，所有调用方导入使用，不在各文件重复定义。
- 常量采用 `UPPER_SNAKE_CASE` 命名，可用 `Final[str]` 标注。常量保存的是**环境变量名**，不是环境变量的值；不要把读取出的值缓存成模块级常量，除非业务明确需要启动时快照。
- 重命名环境变量时，同步更新常量定义、所有引用、`.env`、`.env.example` 及相关测试和文档，遵循上述隐私值处理规则。环境文件中的键仍按其文件格式书写，不用 Python 常量表达式替代。

```python
# constants.py
from typing import Final

DEFAULT_CONFIG_ENV: Final[str] = "DEFAULT_CONFIG"
"""Environment variable specifying the default configuration file path."""
```

```python
# config.py
import os

from .constants import DEFAULT_CONFIG_ENV


def get_default_config_path() -> str | None:
    """Return the configured default file path, or None when unset."""
    return os.getenv(DEFAULT_CONFIG_ENV)
```

### 数据库表名常量

- **Python 代码中的数据库表名必须定义为模块级常量并统一引用，禁止在使用处直接硬编码表名字符串。** 建表、表注册、CRUD、原生 SQL、外键目标及相关测试均遵守此规则。
- 表名集中放在所属持久化模块的公共 `constants.py` 中，采用 `UPPER_SNAKE_CASE` 命名和 `Final[str]` 标注，例如 `SKILLS_TABLE: Final[str] = "skills"`。每个物理表名只定义一次，调用方直接导入，不建立重复常量或可变的全局映射。
- 外键等限定引用从常量组合，例如 `f"{SKILLS_TABLE}.skill_id"`；已有 Table 对象时也可直接使用其 `.c` 列引用，不再重复物理表名。
- 常量化必须保持物理表名、约束及查询行为不变；常量重命名不等于数据库改名。真正修改物理表名时，按项目要求提供已有数据库迁移。
- 独立 `.sql` 迁移文件和历史 schema 固定样本保留其执行所需的物理名称，不导入 Python 常量；不要为消除字符串而改写历史迁移。普通运行时代码和普通 CRUD 测试不属于此例外。

### 数据库列表查询的字段投影

- 返回记录的数据库列表方法如果使用字段投影，应提供可选的 `fields: list[str] | None = None` 参数；`None` 使用该方法明确维护的默认字段列表。不要仅在方法内部写死投影字段，使调用方无法按需选择列。
- 自定义 `fields` 要原样传给数据库查询，并返回与所选列相符的数据；不能把任意投影强行校验为完整记录或默认摘要模型。默认投影仍可使用专门的摘要模型校验。分页过滤和排序所需的列可用于查询条件，不必因此出现在返回字段中；游标构造所需字段由调用方确保包含。
- 只返回布尔值的存在性检查或固定聚合查询没有记录字段选择需求，不必为此添加 `fields` 参数。

## 函数参数与未使用入参

- **函数或方法不需要的入参必须从签名中删除，并在同一次变更中同步删除所有调用方传递的对应实参、文档字符串中的参数说明及相关测试中的旧参数。** 不得为了维持项目内部旧签名而保留无用参数。
- **禁止在函数体中用 `del parameter` 处理未使用入参。** 同样禁止用 `_ = parameter`、改名为 `_parameter` 或添加未使用告警抑制来掩盖无用参数；应修正接口本身。
- 例如，`analyze_trajectories()` 若不使用 `trajectories_by_id`，必须删除该形参及调用处的对应实参，不能保留形参后执行 `del trajectories_by_id`。
- 只有外部框架、回调协议或不可修改的公共接口明确要求固定签名时，才保留协议要求的未使用参数，并用简洁英文注释说明约束；仍不得通过 `del` 伪装成已使用。项目内部可同步修改的接口不属于此例外。

## 注释与文档字符串

- 函数、方法和类的文档字符串统一采用 Google 风格。普通行内注释保持简洁，解释必要的意图和约束。
- **公有函数和方法**必须说明功能，并通过 `Args` 逐项解释参数的实际含义；必要时说明单位、取值范围和空值语义。有返回结果或需调用方处理的异常时，使用 `Returns` / `Yields` 和 `Raises` 说明。无需解释 `self`、`cls`，无参数时不添加空的 `Args`。
- **私有函数和方法**只用一句话解释功能，可以省略参数说明和内部逻辑描述。
- **配置类和数据结构定义中的每个字段或变量**都必须解释物理含义或业务含义，不能只重复类型或变量名；必要时说明单位、范围、默认值及空值语义。采用字段声明后紧跟三引号说明的形式，类本身也写一句功能说明。
- **字段注释必须分组留白。** 字段或变量声明与其自身紧随其后的三引号说明之间不空行；下一字段或变量声明与上一条三引号说明之间必须空一行，禁止将多个“声明 + 说明”组连续堆叠。类文档字符串与首个字段或变量声明之间也必须空一行；`model_config` 等类变量同样遵守此规则。

```python
from datetime import datetime
from enum import StrEnum

from pydantic import BaseModel, ConfigDict, Field


class TrajectoryStatus(StrEnum):
    """Execution status of one trajectory attempt."""

    RUNNING = "running"
    """The trajectory attempt is running."""


class ExecutionInfo(BaseModel):
    """Runtime outcome of one physical trajectory attempt."""

    model_config = ConfigDict(extra="forbid", validate_assignment=True)
    """Reject undeclared fields and validate field assignments."""

    status: TrajectoryStatus = TrajectoryStatus.RUNNING
    """Current execution status of this attempt."""

    started_at: datetime
    """Time when execution started."""

    finished_at: datetime | None = None
    """Time when execution finished; None while execution is unfinished."""

    n_turn: int = Field(default=0, ge=0)
    """Number of agent interaction turns; must be nonnegative."""

    error_info: str | None = None
    """Execution, tool, or environment error details; None when no error details are available."""
```

## 配置与数据结构组织

- **配置类统一放在 `config.py`，非配置的数据结构和类型定义统一放在 `typing.py`。** 此规则适用于模块及其每一级子模块；定义应归属职责对应的模块，不把全项目的数据结构集中到一个巨型文件。
- 同一项目不得混用 `typing.py`、`models.py`、`contracts.py` 等名称承载同类数据结构定义。涉及命名迁移时，同步更新受影响的导入、测试和文档；不要留下重复定义或仅用于保留旧名称的转发文件。
- **数据结构类优先继承 Pydantic `BaseModel`**，配置类也优先使用 `BaseModel`；需要环境变量配置时可使用 Pydantic Settings 的 `BaseSettings`。枚举、类型别名等纯类型定义使用对应的原生类型机制，不强行包装成模型。
- **结构化变量、参数和返回值必须让调用者看得出内容格式，不能只标注 `dict` 或 `Any` 并配一句笼统说明。** 固定字段优先定义具体的数据模型，逐字段注明含义；确实需要动态字典时，标注键和值的类型，并在注释或文档字符串中解释键的含义、值的格式、必填或可选规则及必要示例。仅改成 `dict[str, Any]` 不算说明了结构。
- **参数校验逻辑统一放在类内部。** 优先使用字段类型和 `Field` 约束；单字段自定义校验使用 `field_validator`，跨字段约束使用 `model_validator`。不要在调用方散落或重复实现同一数据结构的参数校验。
- 项目内的 `typing.py` 使用明确的包路径或相对导入，与 Python 标准库 `typing` 的导入区分。

## 模块迁移清理

适用于模块移动、拆分、合并、重命名及大规模重构：

- 迁移完成后，**必须删除原路径上的旧文件**，禁止留下空文件、占位文件，或仅通过 `import` / `from ... import ...` 转发到新模块的兼容文件。所有调用方直接使用新路径，不保留旧路径兼容壳。
- **删除迁移后遗留的空目录**，并逐级清理因此变空的旧父目录；不能通过保留空 `__init__.py` 或其他占位文件维持已废弃的旧包目录。清理范围限于本次迁移产生的残留，不删除仍承担实际职责的包入口或无关文件。
- 完成前同时检查旧路径引用、转发占位文件和空目录，更新受影响的导入、配置、测试与文档，并验证最终清理后的代码可用。

## 大规模模块重构

大规模重构一个模块时，优先在原模块同级创建 `xxx_v2` 模块，并按以下顺序完成迁移：

1. **独立实现完整重构。** 在 `xxx_v2` 内实现全部重构内容；禁止直接或间接导入原模块，也不能通过旧模块的转发、包装或继承复用旧实现。可以使用与旧模块无依赖关系的公共模块和成熟开源包。
2. **逐项迁移并测试。** 盘点所有依赖原模块的调用方、入口、注册项及配置，将它们逐个切换到新模块，每迁移一项就运行相关测试，直至全部切换完成。
3. **完整测试通过后清理旧模块。** 完成重构范围内的完整测试，包括新模块功能、所有迁移调用方以及相关集成与回归测试。测试未通过或仍有必要测试未运行时，不进入旧模块清理阶段。
4. **删除旧模块并恢复正式名称。** 完整测试通过后直接删除旧模块，将 `xxx_v2` 重命名为 `xxx`，同步更新所有导入、路径、配置、注册、测试和文档。禁止保留旧实现、兼容转发层、旧模块别名、失效引用或临时 `_v2` 后缀。
5. **验证最终状态。** 对删除与重命名后的最终代码重新运行上述完整测试，并搜索确认当前代码、配置、测试和文档中没有旧实现或迁移残留，不能只凭重命名前的测试宣布完成。清理针对当前项目中的旧模块及相关引用，不改写 Git 历史或删除无关历史实验产物。

## 显式字段与方法访问

- **配置对象及类似结构化数据的已知字段，必须用显式属性访问**，例如 `config.timeout`；禁止使用 `getattr(config, "timeout")` 或拼接、临时传递字段名字符串读取属性。
- **已知函数和方法必须直接引用或调用**，例如 `agent.run(request)`；禁止通过 `getattr(agent, "run")`、字符串反射或 `eval()` 查找调用目标。
- 同样禁止用 `setattr()`、`hasattr()`、`delattr()` 等字符串属性操作替代已知字段的赋值、接口检查或删除；也不能通过 `__dict__`、`vars()` 或把模型转换成字典后按字符串键读取，绕开显式访问。
- 把属性名或方法名提取成字符串常量不能替代这条要求。环境变量名称常量规则针对外部环境的字符串键；代码内部已知字段、方法和类型关系仍应直接表达，确保重命名可追踪、类型检查可发现遗漏。
- 需要按业务名称选择实现或操作时，使用显式注册表，把业务名称映射到直接引用的类或可调用对象，不把字符串当成属性名或方法名反射。注册加载清单中的模块路径属于导入声明，不用于反射读取配置或方法。
- 对真正以任意键表示的外部 JSON、映射数据，按数据协议访问键；对于具有固定结构的配置或业务数据，先校验成明确的数据模型，再通过属性访问。不要为了方便而把固定结构退化成动态字典。

## 实施与检查

- 修改前查看相邻实现、已有依赖和公共模块，选择最直接、改动最小的实现。
- 优先级是正确性与人类可读性，其次是在此前提下减少代码；“最少代码”不等于最少行数。
- 仅提取真实重复或具有清晰职责边界的逻辑，避免为拆分而拆分。
- 完成后检查：是否重复实现库能力、引入不必要抽象、存在散落的重复逻辑，保留无用入参或用 `del` 等方式掩盖未使用入参，或让读者跨多个文件才能理解简单行为。按项目要求验证实际改变的行为。
