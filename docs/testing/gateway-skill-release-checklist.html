适用：全部发布环境。

编号 级别 建议操作 通过条件
ENV-01 P0 真实部署组合。准备本次发布镜像及生产同类数据库。部署网关、旧 Memory、新 Skill；记录镜像、提交、配置版本和路由。 三个组件版本可追溯；没有用旧构建代替新服务。
ENV-02 P0 健康检查反映依赖。三个服务正常。分别停止 Skill、Memory、Skill 数据库；检查健康接口并调用对应业务。 依赖异常能被识别；不能仅凭网关存活判业务健康；独立业务按约定可用。
ENV-03 P0 独立持久化。新旧两端各有 Skill 和轨迹。单独重启 Skill，再重启网关、Memory；比较数据和关联。 新端已确认写入的数据保留；旧库未被重建或清空。
ENV-04 P0 安全部署配置。发布配置与本地默认配置分离。核对网关地址、签名密钥、鉴权模式、数据库、转发开关、算法开关。 生产启用鉴权；连接目标正确；无本地默认项目或测试密钥。
ENV-05 P1 连接错误可定位。准备错误的内网地址和密钥。分别启动错误配置并调用接口；查看日志和告警。 失败有明确原因且不泄露凭据；不存在成功响应配空结果。
ENV-06 P1 配置变更生效。准备两个可区分的测试上游。按发布流程变更连接和开关；重启或热更新后复测。 生效方式明确；实例配置一致；请求不进入意外环境。

GW 网关路由、协议与错误处理

公网新版入口为 /v2/skills/，网关转到独立服务的 /v1/skills/。旧公网 /v1/skills/* 保持旧协议。验证路由、返回值和故障语义。

适用：全部公开接口。

编号 级别 建议操作 通过条件
GW-01 P0 新旧路由分离。同一项目具备新旧两种 Key 权限。分别用新旧客户端注册、查询 Skill；追踪上游。 旧入口到 Memory，新入口到独立 Skill；没有按同名路径误接协议。
GW-02 P0 业务错误透传。准备不存在的版本、别名冲突和错误参数。通过网关与受控直连接口发送相同请求。 合法业务错误保留 HTTP 状态和业务码；不改成 200 或伪装成空列表。
GW-03 P0 超时结果未知。使写请求在上游提交后超过网关时限。收到超时后查询目标对象，再按幂等契约处理重试。 返回可识别的超时；先查实际结果；不能把超时当作确定未写入。
GW-04 P1 非法请求体。准备损坏 JSON、数组、空体、未知字段。覆盖网关解析与服务模型校验两层。 网关非法 JSON 或非对象返回 400；服务字段校验返回 422；无副作用。
GW-05 P1 错误方法和非白名单。列出服务内部入口及未开放算法。尝试 GET 写接口、拼错操作、额外路径和 train 公网调用。 按冻结契约拒绝；不能绕过网关白名单调用内部能力。
GW-06 P1 异常上游响应。模拟上游重定向、HTML、无 code 字段和 5xx。逐个调用公开 Skill 接口。 网关返回受控服务错误；不跟随不可信重定向；不把 HTML 当成功。
GW-07 P1 链路追踪。客户端携带和不携带请求 ID。覆盖成功、鉴权拒绝、限流、超时、后台任务。 每次请求可定位；网关响应与上下游记录可关联；ID 不混到他人请求。
GW-08 P1 服务未配置和算法开关。分别关闭 Skill 地址与算法开关。调用基础读写和全部算法接口。 未配置返回受控不可用；关闭的算法不暴露；基础能力遵循独立开关。

验收证据：请求与响应、X-Request-ID、网关与上游日志、实际目标地址。

KEY-01 P0 历史 Key 识别。显式 skills:write、旧摘要隐式写权限、新式 memory-only Key。预演补权，比较旧端实际生效权限与候选名单。 只选择原本拥有旧 Skill 权限的 Key；不按名称或 Memory 权限简单推断。

KEY-03 P0 安全属性不变。含有效、过期、撤销、禁用历史 Key。补权后逐项核对值并调用接口。 Key 值、摘要、所属项目、到期和撤销状态不变；失效 Key 不复活。
KEY-04 P0 明确关闭旧权限。历史 Key 已显式关闭旧 Skill 权限。执行补权并调用新接口。 不重新授予新 Skill 权限；内部关闭标记保持有效。
KEY-05 P0 用户撤权后重跑。先补权，再由用户删除新 Skill 权限但保留旧权限。重新运行补权并对比访问能力。 不得无审批覆盖用户明确撤权；若采用一次性补权，重跑边界必须落实并验收。
KEY-06 P0 只读与写权限编辑。Key 有两代 Skill 权限和 Memory 权限。分别只移除新写、移除新读写、关闭旧写、清空可编辑权限。 只影响选择的权限；读写与旧写独立；新读写全移除后新接口不可访问。
KEY-07 P0 非所有者编辑。U2 登录态及 P1 的 key_id。修改、删除、启用他人 Key 或给他人补权。 拒绝操作；不泄露完整 Key；所有者权限保持不变。
KEY-08 P1 预演与重复执行。待补、已补、完全无关 Key 混合。先默认预演，再执行两次 apply。 预演零写入；首轮只补缺失项；次轮无重复项；汇总数字可核对。
KEY-09 P1 中断与坏数据。权限字段损坏、处理中数据库异常。触发失败，修正后重跑。 不留下不可解释的半更新；回滚或已提交范围明确；重跑安全。
KEY-10 P1 补权与用户编辑并发。同一 Key 同时补权和修改权限。控制时序制造冲突并检查最终值。 不丢失用户修改；冲突被报告；重试前重新读取当前权限。
KEY-11 P1 新 Key 默认值。补权完成后创建新项目及新 Key。检查创建默认权限、编辑页面与实际接口权限。 遵循新 Key 的明确默认策略；不会因历史补权给所有新 Key 扩权。

验收证据：补权预演与执行报告、权限前后差异、实际新旧 API 调用、权限编辑审计。

REF-02 P0 歧义拒绝。两个版本正文相同或 ID 前缀碰撞。只提供歧义正文摘要或前缀，再提供精确 ID。 歧义返回明确冲突；精确引用可用；不随机选一个版本。
REF-03 P0 正文与资源共同识别。两个版本正文相同但资源不同。分别加载两份目录并执行识别与轨迹上报。 绑定实际资源对应版本；不只凭正文合并不同 Skill。

REF-06 P1 无匹配和越权匹配。本地未注册 Skill、另一项目相同文件。当前项目执行识别。 不跨项目匹配；未识别原因明确；不伪造版本 ID。

TRAJ 轨迹上报、关联、查询与统计

编号 级别 建议操作 通过条件
TRAJ-01 P0 单版本完整上报。D3 完整对话、状态、时间和执行身份。通过网关 report，再 show、list、statistics。 字段保留；绑定精确版本；回执、详情与统计一致。
TRAJ-02 P0 多版本关联。一条任务实际使用 S1v1 与 S2v2。一次上报两个版本，分别查询两边统计。 一条物理执行关联两版本；按版本统计各一次；不复制成两次执行。
TRAJ-03 P0 空版本列表。Memory 已配置，Skill 版本列表为空。调用组合 trajectory report 并检查两个服务。 Skill 明确 no_skill_versions 跳过；Memory 仍按自身结果上报；不制造空绑定轨迹。
TRAJ-04 P0 无效或跨项目版本。有效和无效版本混合；含 P2 版本。上报后核对轨迹与索引。 失败或局部策略符合冻结契约；不部分成功却返回全成功；无跨项目绑定。
TRAJ-05 P0 重复与补充上报。同一物理执行有稳定标识。客户端重试、网关重试、旧端补绑后重报。 按去重契约保留一次物理执行；合法补绑合并；统计不翻倍。
TRAJ-06 P1 独立重复执行。同 task/session 再运行一次但 execution 标识不同。上报两次，查看明细和计数。 保留两次真实执行；不把同一任务的不同执行错误去重。
TRAJ-07 P1 状态和时间边界。success、failure、unknown；缺开始时间、零分、无分。逐个上报与筛选；加入 UTC 和跨日时间。 未知不伪造成功；零分不同于缺失；时间顺序与时区符合契约。
TRAJ-08 P1 消息结构保真。用户、助手、工具调用、工具结果和无用户消息。上报并查看全文、任务摘要和页面。 消息顺序和角色保留；不凭空生成用户任务；工具内容可定位。
TRAJ-09 P1 执行身份联合过滤。两条执行分别匹配 user 与 agent 的不同条件。组合过滤 user/agent/session/task/status/version。 同一条执行同时满足条件才返回；不把不同执行条件拼接误命中。
TRAJ-10 P1 轨迹分页与摘要。单版本超过 100 条且含长正文。翻页期间新增记录，检查列表和详情。 游标按契约稳定；摘要不代替详情；详情完整；列表不携带不必要的大正文。
TRAJ-11 P0 删除和隐私规则。轨迹关联多个版本；项目需删除数据。按发布的数据保留与删除协议执行。 删除范围、统计和图/评分引用一致；无已删除私密内容通过旧缓存再次出现。

验收证据：上报回执、轨迹详情、版本关联、列表与统计、独立数据库核对。

TASK 异步任务、进度与恢复

接受异步任务不等于任务完成。必须追踪到终态，并核对结果是否真的落库。部署使用的 local 或 Kafka 模式分别验收。

适用：演进及本次开放的后台任务。

编号 级别 建议操作 通过条件
TASK-01 P0 提交到终态。准备可快速完成的演进。提交取得 202 与 task_id；轮询 show/progress 到完成。 接口及时返回；任务归正确项目；成功终态有可查询产物。
TASK-02 P0 失败不伪成功。模型拒绝、无效输入与持久化失败三类任务。分别触发并追踪到终态。 失败原因可读；状态为失败；无伪造候选和已完成提示。
TASK-03 P0 重复提交与并发限制。同项目多个网关和 worker 实例。同时提交评分、组织、演进及相同请求。 执行发布约定的项目容量；冲突可识别；不无限排队或重复收费。
TASK-04 P0 进程重启。任务分别处于 queued 和 running。重启 API、worker；等待恢复或确定失败。 符合所选模式的恢复承诺；无永久假 running；结果不重复发布。
TASK-05 P0 队列不可用。持久化正常但 Kafka 暂停或断网。提交后恢复 broker 与 worker。 若返回已接受则任务可恢复；未接受明确失败；无确认后丢任务。
TASK-06 P1 过期租约和重复消息。running 任务失去 worker；同消息投递两次。等待租约回收并恢复两个 worker。 有效任务只产生一次业务结果；不会双重提交候选。
TASK-07 P1 进度增量。任务产生超过一页进度。按 after 读取，断线后继续；测试负游标与他项目 task_id。 日志无丢页和跨项目数据；非法游标明确拒绝。
TASK-08 P1 模式能力差异。分别核对 local、Kafka 的配置和说明。按实际部署模式执行重启测试并检查不支持能力。 不能用内存模式通过结果代替持久化队列验收；能力限制写入报告。

验收证据：任务 ID、状态序列、进度游标、worker 日志、最终产物和数据库。

MIG-11 P0 扫描中断不算成功。第 2 页源扫描异常或发现阶段中断。运行迁移并检查报告、退出码和汇总。 报告标明扫描不完整；未扫描量不被当成零；禁止以局部数字签收。
MIG-12 P0 迁移与线上写入窗口。迁移扫描同时旧端新增注册、轨迹、evolve。按切流方案运行转发和最终补扫。 迁移前、期间、后的数据均可覆盖；无切换盲区；重叠数据去重。
MIG-13 P1 旧格式保留。历史非标准正文、无时区时间、重名标签。迁移后读取和导出。 保留原文并标记降级格式；时间按约定解释；标签映射可追溯。
MIG-14 P0 无关旧数据不变。旧 Memory、普通轨迹、原 Skill 和用户 Key 基线。迁移前后逐项比较并运行旧客户端。 不删除或重建生产源数据；旧服务持续可用；原权限不被迁移脚本隐式改写。

验收证据：源快照清单、迁移 JSON 报告、ID 映射、逐项目逐对象对账、恢复记录。

Z

RELAY 旧端增量转发与补偿

按目标策略，旧客户端继续写旧端，旧端把应同步的 Skill 和轨迹单向送入新端。后台接受、投递成功和最终对账需要分开判断。

适用：旧端升级后持续流量。

编号 级别 建议操作 通过条件
RELAY-01 P0 旧端新注册立即可迁入。全量迁移完成后创建全新旧 Skill，暂不上报轨迹。旧 SDK 注册后在约定时限内查新端。 按用户目标新增 Skill 自动出现；不能等一次轨迹或 evolve 才证明注册转发通过。
RELAY-02 P0 已有 Skill 新版本。旧端注册更新、云端 evolve 各一组。分别生成新版本并检查新端历史。 两条路径分别验收；父子关系保留；缺祖先能补齐。
RELAY-03 P0 旧轨迹完整转发。已迁版本，旧 SDK 正常 add 携带绑定。检查旧端响应和新端轨迹。 旧 API 按原约定完成；异步转发最终保真；统计不重复。
RELAY-04 P0 轨迹先于版本。新端暂缺对应版本与祖先。发送轨迹，触发缺版本响应再补发。 202 表示待处理；补齐版本后轨迹可查询；没有悬空索引和丢弃。
RELAY-05 P0 旧轨迹后补绑定。先上报 pending 轨迹，再旧端注册对应 Skill。等待补绑并比较同一轨迹。 绑定补全且目标合并原执行；不新增第二条物理轨迹。
RELAY-06 P0 旧删除及新端 active 边界。两端已有迁入家族，新端另有新提交；另建一个同名无关家族。旧端注册后检查新端 active，再从旧端删除迁入家族。 新增版本不自动切换 active；删除软隐藏对应家族及其后续版本，保留快照和轨迹；同名家族不受影响。
RELAY-07 P0 短暂故障恢复。Skill 或网关短暂断网，旧端仍在写。恢复后检查重试及目标。 旧端体验按约定保持；恢复后在时限内补齐；重试不重复。
RELAY-08 P0 重试耗尽补偿。故障持续超过内置重试窗口。恢复服务并执行对账与补扫。 可发现全部遗漏并补齐；日志警告不等于已恢复；无法自动补偿须列上线阻断。
RELAY-09 P0 队列满与进程退出。制造超过队列容量的突发写入并重启 Memory。比较旧库记录集合、新端集合和补扫结果。 已确认旧端数据不永久丢失；缺口可量化并恢复；队列内存丢失不能算成功。
RELAY-10 P0 重放与乱序。同记录重复投递；先子版本后父版本。并行转发及补扫同批数据。 同一目标被幂等合并；谱系完整；无重复统计或旧内容覆盖新内容。
RELAY-11 P0 项目与令牌篡改。合法投递令牌配另一记录或项目。调用网关和 Skill 内部入口。 拒绝不匹配内容；项目取自令牌；不接受请求体任意指定。
RELAY-12 P0 纯 Memory 不触发 Skill。旧 add 不含 Skill 绑定。检查转发流量、两端记录与延迟。 Memory 行为正常；不制造无意义 Skill 轨迹；不增加非必要模型消耗。
RELAY-13 P0 新端独有数据不回流。新端创建 Skill、提交版本、上报轨迹和演进。持续观察旧库及旧 API。 旧端均不新增这些对象；没有双向循环和重复任务。
RELAY-14 P0 旧轨迹后续状态。首条 queued 或 processing 轨迹已成功转发。分别触发 processing、完成、分段输出、失败和取消，再查同一轨迹。 来源状态和完成时间更新；失败及取消原因保留；顶层状态不冒充 Agent 任务结果；物理轨迹仍为一条。
RELAY-15 P0 旧查询接口保持只读。两端已有旧端注册的根版本和子版本。调用旧列表、详情、版本列表、正文和 sync，检查转发队列及新端。 查询保持旧协议且不产生新端写入；sync 不拉取新端独有版本。

验收证据：旧端持久化记录、队列与投递日志、网关内部请求、目标对象、补扫报告。

P27

COMP 新旧客户端共存与升级切换

兼容承诺是旧客户端继续使用旧功能，以及升级后访问已迁历史和新功能。新端独有数据不回写，不能要求旧客户端读取这些数据。

适用：支持矩阵中的每种组合。

编号 级别 建议操作 通过条件
COMP-01 P0 旧旧组合发布前后对比。SDK 0.1.4 与对应旧插件；固定旧业务集。发布前记录基线，发布后原样回放。 原调用、返回关键字段、Skill 注册演化与 Memory 体验保持兼容。
COMP-02 P0 新新组合全链路。新 SDK 与新插件；已迁移历史项目。原 Key 升级后查询历史、创建新 Skill、上报与演进。 路由切新端；历史可见；新功能正常；不要求重建项目。
COMP-03 P0 同项目新旧并行。旧设备 A 与新设备 B 使用同项目。同时产生旧端和新端对象，双向查询。 旧写按策略流入新端；新写仅新端；两设备不覆盖对方数据。
COMP-04 P0 旧插件配新 SDK。实际旧版插件与新版 CLI。分别执行 Memory、显式旧 Skill 引用和旧 Skill 管理流程。 逐项记录兼容范围；Memory 参数兼容不能当作旧注册、自动上传全兼容。
COMP-05 P0 新插件配旧 SDK。两种新插件分别调用 0.1.4 CLI。执行轨迹与默认召回流程。 不支持组合有明确升级提示；不能静默漏报或将命令错误显示为成功。
COMP-06 P1 升级顺序窗口。先升级 SDK、先升级插件两种顺序。在两个升级间隙执行一轮用户任务。 行为与声明支持范围一致；有具体恢复方法；不能要求用户猜测 CLI 环境。
COMP-07 P0 中间版本和自部署。未列入配对区间的版本、自建旧地址。执行版本检测和连接检查。 明确标记未承诺范围；不自动把旧协议当新协议；无数据写错服务。
COMP-08 P0 发布回退边界。新端已接收独有数据；准备旧网关或旧客户端。执行回退演练并恢复新版本。 旧功能恢复；新端数据保留且可重新访问；回退方案不承诺自动反向复制。

验收证据：版本组合记录、真实上游路由、新旧可见数据、升级与降级操作记录。

P28

MEM 原 Memory 能力回归

Skill 拆分不能改变已商用 Memory 服务的数据契约与在线行为。至少覆盖本次改动触及的通路及旧客户端关键业务。

适用：旧、新 SDK；开启与关闭 Skill 转发。

编号 级别 建议操作 通过条件
MEM-01 P0 核心读写回归。历史 Memory 与现网代表性请求。执行 add、search、get、update、delete 及原分页过滤。 原字段与语义保留；旧数据可读写；无数据库重建要求。
MEM-02 P0 异步及流式 Add。历史客户端使用异步和 stream。完成接收、流式输出、查询最终记录。 原返回与事件语义兼容；接收不伪装完成；Skill 后台错误不破坏 Memory。
MEM-03 P0 带旧 Skill 引用 Add。已注册与 pending 引用各一组。旧 SDK 原样 add 后查询 Memory 和轨迹。 原绑定、补绑及 Memory 结果正常；转发只影响预期新端数据。
MEM-04 P0 Skill 故障不拖垮 Memory。关闭新 Skill 或模型依赖。持续旧 Memory 增删查和普通对话上报。 纯 Memory 可用；延迟无失控；后台转发故障隔离。
MEM-05 P0 数据与权限隔离。两用户三项目含历史 Memory。新旧 SDK 混用并切换项目。 Memory 隔离保持；Skill Key 不自动获得未授权 Memory 能力。
MEM-06 P1 本次触及的扩展能力。提测构建启用多模态、图查询或生命周期。回归已上线且受此次改动影响的真实请求。 原数据可访问；字段、链接、搜索和删除语义不退化。
MEM-07 P1 资源竞争。Skill 构图或演进满负载。同时回放代表性 Memory 流量。 Memory 成功率与时延满足冻结阈值；连接池或模型额度无意外抢占。

验收证据：发布前后基线、旧 SDK 结果、Memory 数据、异步记录和跨项目隔离。

P29

FAIL 故障注入、数据一致性与恢复

稳定性验收同时看调用结果和最终数据。数据库、网关、队列或模型失败后，应能解释每次已接受写入的去向。

适用：预发布故障演练环境。

编号 级别 建议操作 通过条件
FAIL-01 P0 数据库写入中断。注册、commit、轨迹关联、图快照各一组。在事务中断开数据库再恢复。 原子提交或回滚；无孤立家族、版本、索引和半快照。
FAIL-02 P0 已提交响应丢失。网关和客户端间断网。写入完成后丢响应，再查询并按契约重试。 能确认真实结果；重复请求无额外业务副作用。
FAIL-03 P0 网关重启。写入和长任务提交正在进行。滚动或强制重启网关。 已接受任务可追踪；身份与项目不丢；失败可重试且不误判成功。
FAIL-04 P0 服务依赖重启。逐个重启 Skill、Memory、数据库与队列。持续正常流量并恢复。 恢复后业务可用；已持久化数据完整；没有长期错误连接或假 running。
FAIL-05 P0 磁盘与存储不可写。Skill 数据盘、日志盘或产物目录空间不足。注册、执行任务和导出。 失败受控；不写部分产物后返回成功；恢复空间后可继续。
FAIL-06 P0 权限中途变化。任务已接受后撤 Key、停项目或撤模型权限。继续短请求并观察后台任务。 按冻结的受理时/执行时授权策略执行；撤权无越权窗口；策略有记录。
FAIL-07 P1 超大请求与并发取消。超过文档上限的正文、消息与资源。从公网入口请求并取消客户端连接。 拒绝可解释；不耗尽内存；取消不产生不可审计的中间结果。
FAIL-08 P1 时钟偏差与短令牌。服务时钟处于允许及超出容差的偏差。测试签名、过期判断与长任务模型调用。 允许范围内稳定；超范围明确失败；无随机越权或永久失效。
FAIL-09 P0 备份恢复。旧库、网关库和 Skill 库有独立备份。在隔离环境恢复并补扫转发。 关键关联与权限可重建；恢复后新旧客户端可用；恢复点和缺口可量化。

验收证据：故障时间线、请求 ID、前后对象清单、任务终态、恢复与对账报告。

P30

PERF 性能、容量与长稳

性能按真实上线规模和业务比例定义。推荐值只是评审起点，提测前由研发、测试和运维共同冻结阈值。

适用：生产同类资源与数据库。

编号 级别 建议操作 通过条件
PERF-01 P0 基础接口负载。小中大正文、80+家族、100+轨迹分页。分别压测 list/show/register/commit/report，再混合压测。 达到已冻结目标 QPS、p95/p99 与错误率；数据一致性零缺陷。
PERF-02 P0 预期峰值并发。冻结的上线峰值及接口比例。至少按峰值持续运行，再按约定倍数突发。 无已确认数据丢失；限流可解释；恢复后积压收敛。
PERF-03 P0 算法与普通接口混合。评分、组织、演进和普通读写流量。达到模型及项目容量边界。 长任务不饿死短请求；不超额执行；Memory 满足原服务目标。
PERF-04 P0 转发积压与追平。旧端流量维持峰值并短时停新端。恢复后测量最旧待转发年龄与追平时间。 达到冻结的延迟及恢复目标；最终源目标对账无缺口。
PERF-05 P1 全量迁移规模。按历史项目数、版本数、轨迹数准备代表性快照。测量迁移吞吐、资源和对在线业务影响。 在部署窗口内完成；扫描完整；在线目标不被迁移打穿。
PERF-06 P0 长稳与泄漏。冻结生产相同比例的混合请求。建议连续 24–72 小时，覆盖任务、重启及补扫。 按约定时长通过；内存、连接、句柄及队列不持续增长；无未知终态。
PERF-07 P1 限流公平性。P1 大流量，P2 正常流量。压满 P1 后观察 P2 与转发流量。 按项目和通道规则公平限流；不因一项目阻塞全部用户。

验收证据：负载脚本、请求比例、基线、p50/p95/p99、错误率、队列水位、资源曲线。

P31

OPS 审计、监控、发布与回退

上线前需要知道故障如何被发现、谁来补偿以及回退后的数据边界。回退新服务不等于把新数据同步回旧服务。

适用：发布放行。

编号 级别 建议操作 通过条件
OPS-01 P0 关键故障可告警。准备上游停机、任务失败、转发积压和补扫失败。分别触发并恢复。 能监测错误率、时延、未完成任务、遗漏量和最旧积压；告警有负责人。
OPS-02 P0 业务全链路可定位。同一用户请求触发后台任务和模型调用。从请求 ID 查到项目、Key 标识、task 与最终对象。 可定位每阶段；无明文 Key、签名令牌、数据库密码泄漏。
OPS-03 P1 审计权限编辑。所有者改权限、撤 Key、补权执行。查看审计、前后差异与操作者。 关键安全变更有追溯；审计内容与实际权限一致。
OPS-04 P0 部署顺序演练。当前线上版本与本次候选版本。先就绪独立 Skill，再兼容网关和旧 Memory，完成转发、迁移对账、补权后放新客户端。 每阶段有可回退检查点；不存在新客户端先切流但历史或权限未就绪的窗口。
OPS-05 P0 不停机升级兼容。旧、新网关实例在滚动期间共存。持续旧 API、新 API 和转发调用。 过渡期协议、签名、字段与权限一致；没有只在某实例失败的请求。
OPS-06 P0 回退演练。已产生新端独有版本及轨迹。回退网关或旧 Memory，再恢复新版本。 旧用户恢复；新库和映射保留；回退后的补偿路径明确；无破坏性源库恢复。
OPS-07 P0 补偿可操作。注入一批已知转发遗漏。由测试按运维文档发现、补扫、复核。 无需人工改业务数据即可闭环；每条遗漏有去向；报告可签收。
OPS-08 P1 文档与提测一致。源码、镜像、SDK/插件构建和迁移说明。按文档从干净环境完成部署与客户端配置。 版本和入口一致；过期的未实现说明被识别；本地通过不冒充线上通过。

验收证据：监控截图、告警触发与恢复、发布演练记录、备份与补偿报告。

P33

迁移与转发对账方法

固定源快照或记录可重放的切换时间边界。 按项目分别建立家族、版本、轨迹、绑定四张明细账。 不要把绑定条数和物理轨迹条数相加。 每条目标对象保留来源标识或稳定映射，排除新端独有对象。

对账对象 必查字段 通过标准
项目 原 project/namespace、所属用户、目标范围 无漏项目、错归属或默认项目兜底
家族 旧 ID、新 ID、名称、别名映射、有效性 一对稳定映射；重复迁移不新增
版本 正文、资源、父子、标签、时间、状态、来源、active 按冻结映射逐字段一致；原文可读可导出
物理轨迹 旧执行 ID、目标 ID、消息、时间、状态、执行身份 每次真实执行恰好一条；重复投递不翻倍
版本绑定 执行 ID × 精确版本 ID 可迁有效绑定齐全；无错绑或悬空索引
Key 原安全属性、原权限、增加权限、用户后续编辑 权限差异有原因；原值与失效状态保留

每类完整扫描集合应满足： 源扫描集合 = 已验证迁入集合 ∪ 明确跳过集合 ∪ 失败集合。 三个集合按该对象主键去重且互斥。 目标中的已验证旧来源集合，应等于成功迁入集合。 新增数与既有验证数分开统计，不能把重跑的零新增当成漏迁。 部分有效绑定必须单列“轨迹已迁、绑定未完整”的记录。

扫描失败时，集合分母未知，不能计算完整迁移成功率。 跳过项须有逐条原因、旧端可用性及用户影响。 任何预期迁入对象失败，都需修复或由发布负责人接受具体例外。 迁移后继续对旧写运行同样的来源对账。 最终补扫必须证明缺口归零，不能只证明命令执行成功。

执行记录与放行

每条正式用例保存：版本组合、环境、数据 ID、步骤、预期、实际结果、证据和缺陷链接。 状态使用：未执行、通过、失败、阻塞、经确认不适用。 阻塞和不适用不计为通过。 P0、P1 的执行率与通过率分别汇报。 同时单列迁移覆盖、转发缺口、Key 补权覆盖和恢复演练结果。

放行条件 所需证据
范围内 P0 全通过 逐条结果；无未关闭的阻断缺陷
范围内 P1 完成回归 未通过项有具体影响、处理人与书面风险结论
历史迁移可签收 完整扫描、逐项目对账、重复执行、中断恢复与例外清单
旧写不永久遗漏 注册、轨迹、evolve 独立通过；积压与故障补偿闭环
权限无意外扩大 原 Key、无关 Key、撤权、失效 Key 和并发编辑证据
两代客户端可用 两种宿主分别验收；支持与不支持组合各有结论
上线可恢复 发布顺序、滚动升级、备份、回退、补扫实际演练

建议执行顺序：环境与路由 → 基础功能与隔离 → 历史迁移 → 转发与客户端兼容 → 算法联调 → 故障、性能与发布演练。 这些阶段可分派给测试人员，但关键完整用户旅程必须串行走通。
